# 流星検出の検証方法

FF（256 フレーム）検出器の検出率・誤検出率を、**感覚ではなく測定**で評価するための手順。
研究計画は `docs/ff-detection-research.md`、一晩の実測は `docs/night-report-YYYYMMDD.md`。

## 1. 評価する量
| 量 | 定義 | メモ |
|---|---|---|
| 検出率（recall） | 実在する流星のうち検出された割合 | 分母は「正解の流星」。作り方は §3 |
| 適合率（precision） | 検出のうち本物の割合 | 誤検出の種類（端ノイズ・衛星・雲・昼間など）を記録 |
| 絶対検出数 | 夜ごとの流星数（検出率で補正） | 検出率が条件で変わるので、条件別に出す |
| 段階別の成績 | A/B/C それぞれの検出数・誤検出数 | 累積（≤A、≤B、≤C）で見る |
| 余裕 | 各ゲートで、最も厳しい本物がどこまで閾値に近いか | 閾値の置き方の根拠 |

## 2. データ
- **全ブロック保存**: 設定 `ff_save_all = true`（検証モード）。検出のないブロックも `ff/` に残る。
  通常は検出＋毎時ベースラインだけ。**検証をする夜は必ずオン**にし、起動ログで確認する。
- **サイドコー**（`FF_*.json`）: 検出器の版（`detector`）、各流星の `tier`/`excess`、リアルタイムイベント、
  `wcs`、時刻同期の統計（`clock`）。
- **動画**（`records/HH/MM.mp4`、1分ファイル、約1MB/分）: 暗い流星の目視確認に使う。
- **時刻**: ログは **UTC**、FITS名・サイドコー・録画のフォルダは **JST（デバイスのローカル時刻）**。混ぜない。
- **壊れたファイル**: 突然の再起動の直前に、サイズ 0 バイトの FITS が出る。解析前に除外する。
- 録画の各ファイルは分の頭から**最大4秒遅れて始まる**（GOP が4秒）。イベント時刻は前後に余白を付けて切る。

## 3. 正解（ラベル）の作り方
正解は「検出器が見つけたものだけ」で作ると**検出器の偏りが正解に入る**。次を併用する。

1. **目視レビュー**: `tools/ff-analysis/offline/ff_review.py` で 1 ブロックずつ見て、`g`=本物 / `x`=誤検出 を `review.csv` に記録。
2. **候補の動画確認**: 検出器が拾わなかった候補（緩い閾値で出るもの）を `tools/ff-analysis/video/ff_clips_cand.py` で動画に切り出し、
   赤枠で位置・時刻を示して目視。FF の画像だけで見える暗い流星は、動画では見えないことがある。
3. **プール方式**: 複数の検出器（自前の段階 A/B/C、リアルタイム、RMS など）の検出の**和集合**を候補にし、
   食い違いを人手で判定する。正解は「プールのうち本物と判定されたもの」。
4. **疑似流星の注入**（未実施）: 検出のない実ブロックに、長さ・速度・明るさ・向きを指定した流星を合成して
   検出器に通す。検出率を明るさ・長さの関数として得られる。絶対数に最も直接効く。
5. **複数局の同時観測**（将来）: 別の局が同時に撮った流星は独立な正解になる。低い段階の検出の救済にも使える。

## 4. オフライン評価パイプライン（`tools/ff-analysis/offline/ff_offline.py`）
`ff.rs` の検出（`ff_detect_meteor`）のPython移植。全ゲートがパラメータで、棄却理由を返す。

```
# 1) 移植が本体と一致するか（保存済み検出のサイドコーと比較）
python tools/ff-analysis/offline/ff_offline.py validate D:/ff/detections/2026/11/14 01 02 03
# 2) 全ブロックのクラスタ数値を一度だけ計算してキャッシュ（超過レベル 15 と 12）
python tools/ff-analysis/offline/ff_offline.py cache D:/ff/2026/11/14 D:/ff/detections/2026/11/14 --hours 00 01 02 03 04 05 --out cache.jsonl
# 3) 段階別の検出率と誤検出を出す（ゲートの判定はメモリ上の比較だけで、すぐ終わる）
python tools/ff-analysis/offline/ff_offline.py tiers cache.jsonl --labels D:/ff/detections/2026/11/14 --true 001505_693 ...
# 4) 緩い閾値で出る候補（取りこぼしの疑い）をコンタクトシートで見る
python tools/ff-analysis/offline/ff_offline.py scan D:/ff/2026/11/14 00 01 02 --relaxed --out cand.jsonl
python tools/ff-analysis/offline/ff_offline.py sheet cand.jsonl --accepted-only --out sheet.png
# 5) 候補を動画に切り出して目視（赤枠付き）
python tools/ff-analysis/video/ff_clips_cand.py cand.jsonl D:/records/2026/11/14 --out clips_candidates
```
- **本体との一致確認**: Python版とRust版（`ff.rs` を切り出して実行）が、2,110ブロックすべてで段階・位置が
  一致することを確認済み。**検出ロジックを変えたら両方を直し、この一致確認をやり直す。**
- **キャッシュ**: クラスタの数値は超過レベルごとに1回だけ計算する。閾値の組み合わせの評価は即時。

## 5. 閾値の決め方
1. 既知の流星の**ゲートごとの値**を表にする（長さ・画素数・直線性・時間相関・速度）。
2. 取りこぼしごとに「どのゲートで落ちたか」を調べる（**1ゲートずつ緩めて**、何が戻るかを見る）。
3. 緩めたときの**副作用**を、非検出ブロックの誤検出数と、既存の検出が失われないかで測る。
   （例: 超過下限を 15→12 にすると、既存の 19 検出のうち 6 件が失われた。フラグ画素が増えてクラスタに
   ノイズが混ざり、PCA の直線性・時間相関が崩れるため。→ 2 つのレベルで別々に検出して和集合を取る。）
4. 1つの閾値で決めきれないものは**段階（信頼度ラベル）**にする: 通った最良の段階を保存する。
5. 1〜2フレームの流星は時間相関が意味を持たない（`maxframe` のスパン≈1）。時間相関に頼らない判定が別に要る。

## 6. 過学習を避ける
- **同じ夜で閾値を決めて、同じ夜で評価しない。** 決めた閾値は凍結し、別の夜で評価する（hold-out）。
- 閾値を変えたら検出器の版（`detector`）を上げ、サイドコーで追えるようにする。
- 条件別に見る: **暗い夜 / 薄明 / 昼間 / 月明かり / 曇り**。2026-11-18 では、暗い夜（11/14）で誤検出ゼロだった
  段階 C が、薄明・昼間では誤検出だらけだった。**段階 C の使い方は、条件（太陽高度、星の数）で決める。**
- 別の局（機材・空・遮蔽物が違う）でも評価する。センサー依存の閾値（ADU の絶対値）は移植できない可能性が高い。

## 7. 他の検出器との比較（RMS）
- RMS（Global Meteor Network）は同じ FF 形式を使う。FITS の形が違う: RMS は「主ヘッダのみ＋4つの画像
  （MAXPIXEL, MAXFRAME, AVEPIXEL, STDPIXEL の順、位置で読む）」で、ヘッダに `NROWS NCOLS NBITS NFRAMES FIRST
  CAMNO FPS` が要る。ファイル名は `FF_<局>_YYYYMMDD_HHMMSS_<ms>_<フレーム>.fits`。変換スクリプトが必要。
- 実行: `python -m RMS.DetectStarsAndMeteors <FFのディレクトリ> -c <設定>`（WSL か Docker。Windows では動かない）。
- **星の数のゲート**: 各 FF で抽出した星が `ff_min_stars`（既定20）未満だと流星検出が実行されない。
  この解像度（640×360）では届かないブロックが多いかもしれない。検出器そのものを比べるときは `ff_min_stars` を
  下げた結果も出す。
- 比較は §3 のプール方式で行い、食い違いを人手で判定する。同じ入力・同じ区間・同じラベルで比べる。

## 8. 夜の前のチェックリスト
1. 設定: `detection_enabled`、`solver_enabled`、**`ff_save_all = true`**、録画・検出の時間帯。起動ログで確認。
2. 時刻同期（NTP）。サイドコーの `clock` で後から確認できる。
3. プレートソルバーの基準姿勢（`solve-lock.json`）。**再キャリブレーションは押さない**（今のところ、レンズの
   事前情報が失われて解けなくなる）。
4. 空き容量（全保存で約330MB/時、8時間で約2.6GB）と、自動削除の設定。
5. 夜の間は**再起動しない・設定を変えない**（突然の再起動でファイルが 0 バイトになる、設定が壊れる）。
6. 朝にまとめて回収: `ff/`、`detections/`、`records/`、`logs/`、`config/`（`atomet.toml` は webhook URL を伏せて共有）。

## 9. SD をクリアするとき
- **消さない**: `factory_t31_*`（カーネル）、`rootfs_hack.squashfs`、`gc2053-t31.bin`、`wpa_supplicant.conf`、
  `hostname`、`time.ini`、`config/`（設定・`mask.bin`・`solve-lock.json`）。
- 消してよい: `ff`、`detections`、`records`、`record`、`stills`、`timelapse`、`time_lapse`、`logs`
  （先にバックアップ。`logs` は不具合の証拠になる）。
