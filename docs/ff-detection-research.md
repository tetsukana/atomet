# FF 流星検出の評価と閾値最適化 — 課題・研究手順・現状

> 関連: 検証方法 `docs/ff-detection-validation-method.md` / 一晩の実測 `docs/night-report-20261118.md`

作成: 2026-11-17 / ブランチ: `dev` / 対象: `crates/atometd/src/{ff.rs,detection.rs}`

> 目的: 閾値を「感覚」ではなく**測定**で決める。そのために、同じ検出器をオフラインで
> パラメータを変えて回せる評価パイプラインを作り、複数ステーション（友人・知人）の
> データで経験的に閾値を決めてリリースする。

## 1. 背景と課題

### 1.1 いまの状況
- 流星検出は2系統ある。
  - **リアルタイム（RT）**: フレーム差分 → セル(8×8px)統計 → ブロブ追跡。`detection.rs`
  - **FF 二次検出**: 256フレーム(約10秒)ごとの `maxpixel/maxframe/avepixel/stdpixel` から
    σクリップ → 連結成分 → 直線性・時間勾配・速度で判定。`ff.rs`
- 閾値は大半が**手で決めた値**で、実データでの根拠が記録されていない（§4.3）。

### 1.2 2026-11-14 01〜05時の初期知見（1晩・1台）
`D:\ff\detections\2026\11\14\` の26ブロックを目視判定（`review.csv`）。

| | FF | RT |
|---|---|---|
| 本物（good）19件の検出 | **18件** | 5件（約26%） |
| 誤検出 | **0件** | 6件（画面左端・上端の1フレーム「ショート」） |

- FFの取りこぼし: `035818`（約36px・6px/frame の速い流星）。**時間相関 0.72 < 閾値 0.8** で棄却。
  直線性・長さ・速度・画素数は通っていた。
- RT の取りこぼしは短い(≲35px)・暗い流星が中心。44px以上は 4/5 を検出。
- RT のショート経路6件はすべて端のノイズ（本物0件）。
- 速度は 5〜31 deg/s（WCS換算）、継続 0.08〜0.84秒 → 流星として妥当。衛星(≈1 deg/s)・
  旅客機(≈1〜5 deg/s, 数秒〜)の帯とは分離できている。
- 流星の向きは19件中18件が画像の下向き。放射点が視野の上にあるため自然な偏り。
- 流星群判定（IAUリスト, `showers.csv`）は軌跡が2〜10°と短く許容幅が6〜15°と広いため、
  偶然一致が約4.7件/19件。確度の高い一致は4件（オフセット約2°以内）のみ。

### 1.2b オフライン再走査の結果（2026-11-14 00〜05時、`tools/ff-analysis/offline/ff_offline.py`）
Python移植版は保存済み検出26ブロックでサイドコーと全件一致。非検出2,084ブロックを走査し、緩い閾値で出た候補を

| ブロック | 内容 | 落ちたゲート |
|---|---|---|

| `025044_090` | 明るい2こぶの線, 長さ21px | 形状（excess 15 では2つに分裂。excess 12 または min_len 8 で検出） |
| `035818_871` | 速い流星, 長さ36px | 時間相関 0.72 < 0.8（`min_corr 0.7` で検出） |
| `022559_406` | 1フレームの短い発光, 長さ10px | 長さ<12 かつ、`maxframe` スパン1で時間相関が意味を持たない |
| `042800_500` | 点状に近い短い流星（目視で流星っぽい） | 直線性・長さ（線として検出できない） |

閾値の副作用（非検出2,084ブロックでの誤検出増加 / 既存19検出への影響）:
- `min_corr 0.8→0.7`: 誤検出+0件、`035818` を回収、既存検出の喪失なし。
- `min_excess 15→12` 単独: `001505`/`025044` を回収するが、**既存19検出のうち6件を失う**
  （フラグ画素が増えてクラスタにノイズが混ざり、PCAの直線性・時間相関が崩れる）。
  → PCA によるクラスタ全体の評価がノイズ画素に弱い。RMS のように線検出（Hough）＋3D線分探索や、
  ロバストな直線当てはめが必要。
- 暫定案: `excess 15` と `excess 12` の2段で別々に検出して和集合（既存を失わず回収）＋ `min_corr 0.7`
  → 既知25件のうち22件（88%）、非検出ブロックの誤検出は増えない（1晩・25件の評価のため過学習に注意）。

### 1.3 課題
1. **絶対検出数が分からない。** 検出率・誤検出率とも未測定。
   （当初「検出なしブロックは保存されない」と書いたが誤り。`ff_is_interesting`（5σ超が10画素）が
   ノイズだけでもほぼ常に真になるため、実際は**ほぼ全ブロックが保存されている**。
   2026-11-14 は 00〜10時で1時間あたり約313〜352ブロック（満杯は約351）。
   → 偽陰性の評価データは既にある。課題は「正解ラベルが無いこと」。）
2. **閾値の根拠がない。** 時間相関0.8・直線性5・最小長12px・最小画素12 などは未検証（§4.3）。
3. **検出器が走っている最中にしか評価できない。** パラメータを変えて再実行できない。
4. **1台・1か所・1晩のデータ**で、空の明るさ・レンズ・センサー・遮蔽物が固定されている。
   他環境で通用するか不明（過学習のリスク）。
5. **RT が FF の保存判定を汚している**（RT誤検出だけでブロックが `detected` 保存される）。
6. 動画録画が RT 信号に依存（FFだけにできない）。

## 2. 研究のゴールと評価指標

| 指標 | 定義 | 取得方法 |
|---|---|---|
| 検出率（recall） | 実在する流星のうち検出した割合 | §3.2 の3手法で推定 |
| 適合率（precision） | 検出のうち本物の割合 | 目視ラベル（§3.1） |
| 絶対検出数 | 夜ごとの流星数（補正後） | recall で補正した推定値 |
| 検出限界 | 明るさ・長さ・速度ごとの recall 曲線 | 疑似流星の注入（§3.2-B） |
| 誤検出の種類別内訳 | 端ノイズ/航空機/雲/雷/… | 目視ラベルにタグ付け |

最終目標: **「この閾値なら recall X% @ 誤検出 Y件/夜」と言える設定**を、環境別プロファイル付きで出す。

## 3. 研究手順（案）

### 3.1 データとラベル
- **全ブロックの保存**: 現状でもほぼ全ブロックが `ff/` に保存されている（`interesting` 判定が常時真になるため）。
  ただしこれは偶然の挙動で、閾値や条件を変えると保存されなくなる。評価用には明示的な「全保存」モードにして固定する。
  （以下は明示モードにした場合の概算）
  gzip で約 0.5MB/ブロック（元 0.95MB）、約 190MB/時、8時間で約 1.5GB。
  ave/std は滑らかなので量子化・差分化でさらに圧縮可能。常時ではなく**期間限定の評価モード**とする。
- **ラベル**: 既存の `review.csv`（good/false）を拡張し、`reason`（端ノイズ/航空機/雲/…）、
  `confidence`、`reviewer` を持たせる。複数人でラベルして一致度も測る。
- **動画**: 1分あたり約1MBの通常録画は、暗い流星も確認できる（`022630` で確認済み）。
  常時録画を夜間は有効にすると、FF検出時刻からクリップを自動で切り出せる。

### 3.2 絶対検出数・recall の推定（正解が無いので3手法を併用）
- **A. 複数検出器の相互比較（捕獲-再捕獲）**: FF・RT・人手（動画/全ブロック目視）の独立な
  検出集合から Lincoln–Petersen 等で母数を推定。独立性の仮定に注意。
- **B. 疑似流星の注入（injection–recovery）**: 検出なしの実ブロックに、既知の
  （長さ・速度・明るさ・向き・時間勾配）の流星を合成して検出器に通し、recall 曲線を得る。
  **絶対数に最も直接効く**。実センサーのノイズ特性をそのまま使える。
- **C. 複数局の同時観測**: 近隣の別局が同時に撮った流星は、独立な正解になる
  （軌跡の三角測量も可能）。友人・知人のデータが貯まれば最強のラベル。

### 3.3 オフライン評価パイプライン
- 検出ロジックを**共有クレート**に切り出し（例 `crates/ffdetect`）、ファームウェアとオフラインCLI
  が**同じコード**を使う（再実装による乖離を避ける）。現状は `atometd/src/ff.rs` 内。
- 入力: 保存済みブロック（FITS）＋ ラベル。出力: パラメータ組ごとの TP/FP/FN、recall/precision、
  ROC/PR、各閾値の**余裕**（最も厳しい本物がどこまで下がるか）。
- パラメータ走査: グリッド／ランダム／ベイズ最適化。**環境ごとに別々に最適化**し、
  共通部分と環境依存部分を分ける。
- 検出の再現性: 検出に使ったパラメータ・検出器バージョンをサイドコー(`json`)に書き込む
  （現状は書いていないため追加）。

### 3.4 閾値の決め方
1. 各閾値について、ラベル済み流星の**最小余裕**と、誤検出側の**最大値**を表にする。
2. 両者の間に分離があれば、その中間に置く。重なるなら、他の判定（複合条件）で補う。
3. 取りこぼしの典型（速い少フレーム流星など）は、閾値ではなく**別経路の判定**で拾う。
4. 過学習を避けるため、**ステーション単位で hold-out**（学習局と検証局を分ける）。

### 3.5 リリース
- 設定を「閾値＋環境プロファイル」として配布（`/media/mmc/config/` に上書き可能にする。
  流星群リスト `showers.csv` と同じ方式）。
- 友人・知人向けのバージョンリリース（§5）。評価モードで取ったデータを提供してもらい、
  プロファイルを更新する。

## 4. 現行の検出パイプラインと閾値

### 4.1 全体構成
```
luma(640×360, 25fps) ──┬─ detection.rs (RT)  → meteor/meteor_end イベント
                       │                       → stack.png / 検出トリガー録画 / UI / webhook
                       └─ ff_stack_worker    → 256フレームごとに FfBlock
                                                 ↓
                         ff_save_smart_task: ff_detect_meteor (σクリップ+直線+時間勾配)
                                                 ↓ 検出 or RT検出あり or interesting or 毎時1ブロック
                         FITS(max/frame/ave/std) + sidecar json + WCS + 流星群判定
```
保存条件（`ff_save_smart_task`）: `detected`(FF検出 or **RT検出が1件でもあった**) /
`baseline`(毎時1ブロック) / **`validation`**(設定 `ff_save_all` がオンのとき全ブロック)。
（2026-11-18 に変更: 以前は `interesting`＝5σ超が10画素 も保存条件だったが、ノイズだけでもほぼ常に真になり
全ブロックが保存されていたため廃止し、明示的な検証モード `ff_save_all`（既定オフ）に分離。WS コマンド `set_ff_save_all`。
WebUI のトグルは未実装。この環境ではクロスビルドできず未コンパイル。）
**ただし `interesting`（5σ超が10画素以上、絶対下限なし）はノイズだけでもほぼ常に真**なので、
実際には**ほぼ全ブロックが `ff/`（通常保存）に残る**（2026-11-14: 00〜10時で約95%）。
これは意図した挙動ではなく、閾値を変えると保存が途切れる。

### 4.2 FF 二次検出（`ff.rs`）
1. 画素ごとのσクリップ: `max − ave > SIGMA_K·max(std,1)` かつ `> FF_DET_MIN_EXCESS`。マスクセルは除外。
   フラグ総数が `FF_DET_MAX_PIXELS` を超えたら全棄却（雷・照明の急変）。
2. 3×3膨張で連結（クラスタ分けのみに使用。メンバーは元のフラグ画素）→ フラッドフィル。
3. クラスタごとに `analyze_cluster`:
   - PCA: 直線性 λ1/λ2、長さ √(12λ1)
   - 位置（主軸への射影）と `maxframe` の Pearson 相関
   - 見かけ速度 = 長さ / (最大フレーム − 最小フレーム)
4. 画素数の大きい順に最大8件。`fps` は実測値で補正（混在fpsのブロックは解析しない）。

### 4.3 FF の閾値
| 定数 | 値 | 役割 | 根拠の記録 |
|---|---|---|---|
| `SIGMA_K` | 5.0 | σクリップ倍率 | 一般的な値。根拠記述なし |
| `FF_DET_MIN_EXCESS` | 15 ADU | `max−ave` の絶対下限 | あり（stdが整数丸めで5σ≈ノイズ） |
| `FF_DET_MAX_PIXELS` | 20,000 | 総フラグ画素の上限 | あり（雷・照明、雲は数百画素） |
| `FF_DET_MIN_PIXELS` | 12 | クラスタ最小画素数 | なし |
| `FF_DET_MIN_LINEARITY` | 5.0 | λ1/λ2 | なし |
| `FF_DET_MIN_LEN_PX` | 12 | 最小長さ | なし |
| `FF_DET_MIN_TIME_CORR` | 0.8 | 位置×maxframe の \|r\| | なし（**`035818` を棄却**） |
| `FF_DET_MIN_SPEED_PX` | 0.8 px/frame @25fps | 衛星除外 | あり（衛星は約10秒で横断） |
| `FF_DET_MAX_METEORS` | 8 | 1ブロックの最大件数 | — |
| `MIN_INTERESTING_PIXELS` | 10 | 「interesting」判定 | — |
| （無し） | — | **継続時間の上限** | RT側にはあり（約3秒）。FFには無い |

**信頼度の段階（2026-11-18、`ff.rs` に実装）**: 閾値を1組で決め打ちせず、段階 A/B/C で検出し、
通った最良の段階をラベルにする（イベント・サイドコーの `tier`、サイドコー `detector: "ff-tier-v1"`）。
σクリップは超過下限 15 と 12 の2レベルで実行し、同じ場所（中心が15px以内）は最良の段階を残す。

| 段階 | 超過レベル | 画素 | 直線性 | 長さ | 時間相関 | 速度 | 縁 |
|---|---|---|---|---|---|---|---|
| A（従来と同じ） | 15 | ≥12 | ≥5 | ≥12 | ≥0.8 | ≥0.8 | 制限なし |
| B | 15, 12 | ≥12 | ≥5 | ≥12 | ≥0.7 | ≥0.8 | 8px除外 |
| C | 15, 12 | ≥8 | ≥3 | ≥8 | ≥0.5 | ≥0.4 | 8px除外 |

2026-11-14 00〜05時（既知の流星26件、2,110ブロック）: A=19、B=3、C=4（累積26件）、誤検出0。
Rust版とPython版(`tools/ff-analysis/offline/ff_offline.py`)は全2,110ブロックで段階・位置が一致。**1晩・同じデータで決めた値なので、
他の夜で再確認が必要。**

### 4.4 リアルタイム検出（`detection.rs`）
1. 毎フレーム: 前フレームとの飽和差分を8×8セルに集計（80×45）。
2. セルごとに、フレーム内MAD z（`SPATIAL_THRESHOLD`）、セル別EMAのz（`TEMPORAL_THRESHOLD`）、
   絶対差 `MIN_CELL_DELTA` を同時に満たしたセルを「点灯」。
3. ブロブ化（8近傍）→ 近接ブロブ併合（`BLOB_MERGE_GAP`）→ 巨大ブロブ除外（`MAX_BLOB_CELLS`）。
4. ピクセル級のストリーク形状（`streak_stats`: 輝度加重2次モーメント）。
5. トラッカ: 速度予測＋最近傍で関連付け、PCAで直線性・単調性・速度を判定。
6. **ショート経路**: 追跡が `SHORT_MAX_FRAMES`(3) 以内で終わったものは、1フレームの形状
   （伸長・長さ・フラックス）のみで判定。

| 定数 | 値 | 備考 |
|---|---|---|
| `SPATIAL_THRESHOLD` / `TEMPORAL_THRESHOLD` | 6.0 / 5.0 | セル判定 |
| `MIN_CELL_DELTA` | 6.0 | 中央値からの絶対差 |
| `EMA_ALPHA` / `EMA_CLAMP_SIGMA` | 0.05 / 3.0 | 統計の更新（毎フレーム、fpsで補正） |
| `MAX_BLOB_CELLS` | N_CELLS/8 | 画面規模の発光を除外 |
| `STREAK_MIN_ELONG` / `_LEN_PX` / `_FLUX` | 6.0 / 16 / 300 | ショート経路 |
| `TRACK_MAX_DIST` / `_MAX_MISSED` | 5セル / 2 | 関連付け |
| `TRACK_MIN_FRAMES` / `_MIN_DISP_SQ` | 4 / 4.0 | 確定条件 |
| `TRACK_MIN_LINEARITY` / `_MIN_MONOTONIC` | 12 / 0.8 | 確定条件 |
| `TRACK_MIN_SPEED_CELLS` | 0.0625 | 0.5 px/frame |
| `TRACK_MAX_EVENT_FRAMES` | 75 | 約3秒。超えると航空機・衛星として降格 |

> 既知の問題: ショート経路は画面端（x または y がセル0）で1フレームだけ光る誤検出を出す
> （今夜 6/6 が端）。端のセルでのショート棄却、または2フレーム以上の継続要求で対処できそう。

### 4.5 先行研究との比較（RMS / Global Meteor Network）

RMS（Raspberry Pi Meteor Station, Croatian Meteor Network）は、同じ FF 形式（256フレームの
max/avg/std/maxframe, Gural の FTP 圧縮）を使う最大の先行例。

出典（読んだもの）:
- [RMS `.config`](https://raw.githubusercontent.com/CroatianMeteorNetwork/RMS/master/.config) — 全パラメータの既定値と注釈（全文確認）
- [RMS `Detection.py`](https://raw.githubusercontent.com/CroatianMeteorNetwork/RMS/master/RMS/Detection.py) — 先頭約4万字は原文確認、残りは要約のみ
- [Vida et al. 2021, GMN Methodology and First Results (arXiv 2107.12335)](https://arxiv.org/abs/2107.12335) §2.2 検出 — ar5iv版の約7.9万字を原文確認
- 未確認: 論文の後半約12万字、Gural の FTP 圧縮の原論文、検出効率を扱う論文（GMN フラックス論文
  [arXiv 2206.11365](https://arxiv.org/abs/2206.11365) が候補）

**RMS の検出手順**（`detectMeteors`）
1. avg/std は「最大値上位4つ」を除いて計算（イベント自身による汚染を避ける）。
2. 256フレーム全体の avg/std で `max > avg + K1·σ + J1` を二値化し、**`maxframe` が64フレーム窓（32刻み）に入る画素ごと**に以降を処理。
3. 形態学処理（clean→bridge→close→thin→clean）で細線化。`max_white_ratio=0.05` を超えたら画像ごと棄却。
4. Kernel-based Hough Transform で線候補 → X,Y,フレームの**3D線分探索**（時間の連続性を確認）。
5. 受理条件: **4フレーム以上連続**、**角速度 2〜51 deg/s**、画像/マスクの縁から5px以上離れている。
6. 中心位置・強度を各フレームで再計算。外れ値除去（`filterCentroids`）、任意で ML フィルタ（`ml_filter: 0.85`）。
7. 淡い流星用の検出は **星が20個以上見えるとき（晴天）だけ** 実行。明るい火球は別経路（K1=7, J1=10）。

**閾値の比較**
| 項目 | RMS（GMN既定, IMX291） | atomet（現行） |
|---|---|---|
| 二値化 | `max > avg + 3.5σ + 12`（加算形） | `max−ave > 5σ` **かつ** `> 15`（AND） |
| 時間窓 | `maxframe` で64フレーム窓・32刻みに分割（統計は256フレーム全体） | 分割なし（連結成分ごとに判定） |
| 線の判定 | KHT + 3D線分探索 | PCA直線性≥5 + `maxframe`相関≥0.8 |
| 最小フレーム数 | **4** | **なし**（`frames`=2,3 の検出あり） |
| 角速度 | 2〜51 deg/s | 下限のみ（0.8 px/f ≈ 3.2 deg/s）、上限なし |
| 継続時間の上限 | なし（RMS側では未確認） | FFは無し／RTは約3秒 |
| 縁の除外 | `detection_border: 5` px | なし |
| 晴天判定 | 星20個未満では淡い検出を実行しない | なし（`StarTracker` の星数が使える） |
| 全面発光の棄却 | 二値化後の白画素比 5% | 総フラグ画素 20,000（≈8.7%） |
| avg/std | 上位4値を除外 | 全256フレームを含む |
| 誤検出の機械学習フィルタ | あり（`ml_filter`） | なし |

**学べる点・取り込み候補**
1. **縁の除外**（`detection_border`）: 今夜の RT の端ノイズ6件と同じ問題に、RMS は設定で対処済み。
2. **`maxframe` による時間窓（64フレーム）**: 二値化は256フレーム全体の avg/std で1回だけ行い、窓は
   「`maxframe` が窓内の画素だけ」を取り出すために使う（`getLines` は `thresholdFF` を1回呼び、窓ごとに
   `FFfile.selectFFFrames(img_thres, ff, frame_min, frame_max)` で選別する。`selectFFFrames` の中身は
   未読だが、名前から `maxframe` による選別とみられる）。感度向上ではなく、時間的に
   離れた別事象を分離して線検出にかけるのが目的。atomet は連結成分＋`maxframe`相関で代用している。
3. **最小フレーム数の扱い**: RMS は4フレーム必須。今夜の本物には、FF の `maxframe` スパンが2〜3の流星
   （`024911` など）があり、RMS 基準では落ちるはず。**`maxframe` スパン（ピーク時刻の幅）は検出時間より短い**ため、
   同じ数値で比べられない点に注意。ここは実データで確認が必要。
4. **晴天ゲート**: 星数が少ない（曇り）とき閾値を上げる／検出しない、は誤検出抑制に有効そう。
5. **avg/std から上位値を除外**: 明るい流星が std を膨らませて自身を隠すのを防ぐ。
6. **センサーごとの J1**: GMN の「K1=3.5, J1=12」は **IMX291 向けの既定値**として書かれており、
   他センサーは未検討とみられる。atomet は GC2053 なので**自前の調整が必要**（本研究の根拠）。

**重要な発見: 先行研究にも検出効率の評価は見当たらない**
- 論文の読めた範囲に、検出率・完全性・誤検出率・閾値の調整根拠の記述はない（K1/J1 は「よく使う値」として提示）。
- 感度は「恒星限界等級 +6.0±0.5」で表現されている。流星の検出限界との対応は、別論文
  （フラックス論文）の扱い。
- つまり **疑似流星注入などによる検出効率の定量評価は、本研究の独自性になり得る**（要・後半と関連論文の確認）。
- 参考: RMS の docstring（0.5〜35 deg/s）と設定値（2〜51 deg/s）が食い違っている箇所があり、
  RMS 自身も閾値の運用は経験的。

### 5.1 環境差の論点（自宅1か所からの一般化）

- 遮蔽物（建物・木）とマスク。マスクの作り方の標準化。
- 時刻同期（NTP, `clockstat`）。複数局の同時観測（§3.2-C）には数十ms〜数百msの精度が必要。
- 録画・保存容量の違い。
